# Customer Portal security

Signed portal and payment-method URLs are bearer capabilities. They are retrieved fresh on click and are never stored in database rows, React Query result data, local/session storage, logs, or Sentry. The frontend mutation navigates internally and returns void, with retries disabled and zero cache retention. Request bodies contain purpose only. Successful responses contain purpose, portalUrl and optional safely derived expiresAt; failures contain a safe code only. Every response, including failures, has `Cache-Control: no-store, private` and `Pragma: no-cache`.

## Authorization and URL boundary

Supabase `getUser` authenticates the caller. A service-only resolver validates canonical PT identity, resolves the owned billing account, chooses the current local subscription (or latest terminal history), and requires a paid provider link in the server environment and configured Store. Customer mapping and local linkage must agree. No email-based ownership inference occurs. The resolver is called again after provider retrieval to detect ownership/linkage changes. The owner-facing summary RPC returns no provider identifiers or capability URL. It cannot accept a target account.

`BILLING_PORTAL_ALLOWED_HOSTS` is a server-only comma-separated list of exact bare DNS hosts, including explicitly approved custom domains. Wildcards, schemes and ports are rejected. Nothing reads a browser-configurable allowlist. URL parsing requires HTTPS, no user/password, no port/fragment, an exact allowed host, and the purpose-specific path: `/billing` or `/subscription/<resolved-provider-subscription-id>/payment-details`. Upgrade paths are not accepted. Query parameters are limited to one 64-hex signature and optional single positive future Unix-seconds expires. Missing URLs, malformed paths, duplicate parameters, expired links and unknown hosts fail safely. RepSync validates signature structure, not the provider's cryptographic signature; the trusted authenticated provider API supplies it. It never constructs a signed capability itself.

The adapter uses the existing fixed provider API origin, rejects redirects and requests no-store. Provider 429, timeout, network and parse errors map to safe portal errors. Raw provider responses, credentials, signatures, identity fields, card data, addresses and tax information are never logged. Operational logging uses safe error code and processing status only; unapproved-plan-change telemetry contains no provider identifiers.

## Telemetry and browser artifacts

The shared payment URL scrubber now removes official provider URLs, custom-domain billing/payment-detail paths and signed URLs from nested messages, exceptions, breadcrumbs, structured attributes and URL-bearing keys. Explicit portalUrl/customer_portal/update_payment_method/signature fields are redacted. Sentry applies it to events, transactions, console breadcrumbs and structured/console logs via beforeSendLog. Portal application code never logs raw errors or capabilities. The scrubber is a stateless utility, not provider startup state.

Deterministic tests construct synthetic signatures in memory; no real signed URL is committed. Portal browser tests disable tracing and video to avoid persisting capability-bearing navigation. Production operator proof must likewise avoid HARs, traces, screenshots of address bars and copy/paste of capability URLs into tickets. Browser navigation necessarily receives the capability in memory; no claim is made that the browser/provider can operate without seeing its URL.

Dashboard configuration cannot authorize a RepSync plan change. Immutable Product/Variant/Price mismatch causes durable manual review, no local plan/capacity mutation, and sanitized telemetry. A matching current snapshot can clear review under the corrected PR-PRICE-05 contract; stale/invalid snapshots cannot.
