# Customer Portal security

Signed portal and payment-method URLs are bearer capabilities. They are retrieved fresh on click and are never stored in database rows, React Query result data, local/session storage, logs, or Sentry. The frontend mutation navigates internally and returns void, with retries disabled and zero cache retention. Request bodies contain purpose only. Successful responses contain purpose and the unchanged portalUrl; failures contain a safe code only. No expiresAt is derived from the provider query. Every response, including failures, has `Cache-Control: no-store, private` and `Pragma: no-cache`.

## Authorization and URL boundary

Supabase `getUser` authenticates the caller. A service-only resolver validates canonical PT identity, resolves the owned billing account, chooses the current local subscription (or latest terminal history), and requires a paid provider link in the server environment and configured Store. Customer mapping and local linkage must agree. No email-based ownership inference occurs. The resolver is called again after provider retrieval to detect ownership/linkage changes. The owner-facing summary RPC returns no provider identifiers or capability URL. It cannot accept a target account.

`BILLING_PORTAL_ALLOWED_HOSTS` is a server-only comma-separated list of exact bare DNS hosts, including explicitly approved custom domains. Wildcards, schemes and ports are rejected. Nothing reads a browser-configurable allowlist. URLs must be strings of at most 4096 characters, parse successfully, use HTTPS, and contain no whitespace, backslashes, username, password, explicit port (including :443), or fragment (including an empty #). The parsed hostname must exactly match an allowed host. The parsed path must be `/billing` or `/billing/` for `manage_billing`, or `/subscription/<resolved-provider-subscription-id>/payment-details` with at most one trailing slash for `update_payment_method`. Descendant/upgrade paths, wrong subscription IDs, unrelated paths and encoded paths that do not normalize to an allowed path are rejected.

The signed query string is provider-owned opaque capability data. RepSync validates provenance through the authenticated provider API plus canonical identity/ownership checks, and validates the URL transport/origin/path boundary. It does not reinterpret provider signature parameters.

For both purposes, RepSync preserves the complete original URL, including query order, repeated keys, encoding and future provider fields. It neither enumerates query keys nor validates signature, expiry or user values. No query value is used for RepSync authentication, authorization, ownership or routing, including values named redirect or environment. The provider is responsible for interpreting its capability and enforcing signature validity and expiry. The [official provider guide](https://docs.lemonsqueezy.com/guides/developer-guide/customer-portal) recommends retrieving and consuming the returned URL on click.

A URL with no query string (or an empty query) is accepted only through the same authenticated provider-origin and identity/ownership contract. Query presence is not proof of authorization; the provider determines whether its destination needs a sign-in flow. Missing/null URL fields remain unavailable: RepSync never constructs a fallback URL or accepts a browser-supplied destination. All returned URLs remain sensitive for logging, caching and evidence purposes, regardless of query shape.

The adapter uses the existing fixed provider API origin, rejects redirects and requests no-store. Provider 429, timeout, network and parse errors map to safe portal errors. Raw provider responses, credentials, signatures, identity fields, card data, addresses and tax information are never logged. Operational logging uses safe error code and processing status only; unapproved-plan-change telemetry contains no provider identifiers.

## Telemetry and browser artifacts

The shared payment URL scrubber now removes official provider URLs, custom-domain billing/payment-detail paths and signed URLs from nested messages, exceptions, breadcrumbs, structured attributes and URL-bearing keys. Explicit portalUrl/customer_portal/update_payment_method/signature fields are redacted. Sentry applies it to events, transactions, console breadcrumbs and structured/console logs via beforeSendLog. Portal application code never logs raw errors or capabilities. The scrubber is a stateless utility, not provider startup state.

Deterministic tests construct synthetic signatures in memory; no real signed URL is committed. Portal browser tests disable tracing and video to avoid persisting capability-bearing navigation. Production operator proof must likewise avoid HARs, traces, screenshots of address bars and copy/paste of capability URLs into tickets. Browser navigation necessarily receives the capability in memory; no claim is made that the browser/provider can operate without seeing its URL.

Dashboard configuration cannot authorize a RepSync plan change. Immutable Product/Variant/Price mismatch causes durable manual review, no local plan/capacity mutation, and sanitized telemetry. A matching current snapshot can clear review under the corrected PR-PRICE-05 contract; stale/invalid snapshots cannot. See the [runbook](lemon-squeezy-portal-test-runbook.md) before any separately approved provider exercise.
