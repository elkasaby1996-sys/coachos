# GitHub approval evidence qualification

CODEX-BILL-03A adds an offline diagnostic evaluator only. It does not authenticate
HTTP records, JWTs or webhooks, supply a founder workflow proof, claim an action,
read credentials, call GitHub or integrate with release execution. Its output
always has `operational: false`; matching fields are explicitly labelled
`matches_documented_fields`, never authenticated approval.

Contract inspection date: 2026-10-10. No repository API, environment configuration,
actual approval, operational identity or hosted capability was inspected.

## Evidence matrix

after a future trusted reader authenticates acquisition and binds its exact request.
It does not mean this offline module authenticates them. Reader permissions below
refer to GitHub App/fine-grained repository permissions; private resources need
appropriate access. No write permissions are needed for these reads.

## Offline input and output

`evaluateFounderGitHubEvidence({ expected, evidence, now })` takes explicit time
and reviewed expectations supplied by the caller. Synthetic IDs are never enrolled.
There is no network, environment, filesystem, credential or callback parameter.

REST fixture records use this local acquisition envelope:

```text
{ request, observedAt, status, headers: { link, rateLimitRemaining },
  transportError, body }
```

`request` contains a fixed repository and applicable run/attempt/ref/workflow/
environment/page/filter identifiers and optional `perPage` (1–100). These are reader metadata, not invented
GitHub response fields. The future reader must authenticate and bind them.
API failure bodies are never returned. Timeout/network errors have null status.

Jobs and check runs use arrays of page envelopes with documented `total_count`.
Active rules use arrays of page envelopes whose bodies are arrays (no invented
`total_count`). Pages must be ordered, request-bound, and terminate without a
next link. Every page must retain the same request identity except for its
contiguous page number, including the presence and value of `perPage`. Omitted
`perPage` means GitHub's default of 30. Every Link relation must use the fixed
endpoint, ref/filter contract and the same effective page size (`per_page`,
also defaulting to 30). Counted lists also require consistent totals and unique
row IDs. Consistent pagination alone proves neither an immutable remote snapshot
nor authenticated completeness.
All supplied reads must be no older than the existing 15-minute freshness bound;
future acquisition timestamps block. Fetch freshness cannot date an approval.

Optional webhook fixtures contain `{ observedAt, payload }`; OIDC fixtures contain
`{ observedAt, claims }`. Neither accepts a caller-supplied authenticated flag.
Unrelated API body fields are discarded by narrow projections. For example,
adding `bypassUsed: false` to a review body does not create a documented predicate.

Results distinguish explicit contradictions/denials from unavailable, malformed,
stale, ambiguous or unsupported evidence. All results remain non-operational.
They cannot satisfy `validateFounderAction()` or `beginFounderOperation()`.
The existing signatures, hooks, policy, workflows and replay boundary are unchanged.

`app.id` identifies the publisher App, not its originating workflow. Matching the
supported check inventory does not certify workflow-based rules, legacy status
contexts, protection bypass actors or historical enforcement. Those require
separate qualification. Link headers are only parsed against fixed GitHub paths;
the module never follows them or accepts a URL selecting a transport endpoint.

## Qualification boundary

The GitHub documentation describes `workflow_run` as nullable, whereas Octokit's
approved-event schema references a non-null workflow run with `run_attempt`.
The adapter compares that documented nested identity when present and marks null
association unsupported. This schema difference requires hosted qualification;
it must not be resolved by inventing fields. Matching event fields still does
not prove authenticated normal admission or no-bypass. `since` is not promoted
to an authenticated approval timestamp.

The local delta is reviewable independently of whether GitHub can meet the full
admission contract. Do not build an operational verifier, enroll keys or enable
governance on the strength of these diagnostics. A future separately authorized
qualification must establish authenticated exact-attempt normal approval and
historical no-bypass semantics, including real webhook/API association and access
coverage. If it cannot, the existing contract remains blocked; do not infer an
approval, introduce a synthetic bypass flag or relax the predicate.
