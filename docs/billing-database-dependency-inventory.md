# BILLING-ADAPTER-03 database dependency inventory

Design evidence at repository commit `4718508`, 2026-09-19. Read alongside [the proposed compatibility design](billing-database-compatibility-design.md). This inventories repository-defined behavior, not the state of a deployed database. No database connection was made.

## Classification

The requested categories overlap: ownership and migration disposition are separate axes. Each field/constraint below receives an ownership class and, where relevant, a disposition:

- **1 / C**: RepSync-owned canonical identity, commercial policy, lifecycle, or audit data. Preserve semantics.
- **2 / G**: generic provider identity/evidence concept. External references are opaque and scoped.
- **3 / L**: Lemon-Squeezy-specific historical contract.
- **4 / S**: safe to generalize **in a new versioned contract**, with the stated invariants; not permission to rewrite history.
- **5 / K**: must remain legacy, including the meaning and bytes of existing persisted evidence.

`G/S` means categories 2 and 4; `L/K` means 3 and 5. Generic historical identifiers are `G/K` when discussing their existing persisted value. Every row lists all covered fields; common groups are explicitly named rather than inferred from naming prefixes.

Trusted service role has explicit orchestration RPCs; apply helpers are not service-callable standalone. Functions use fixed `search_path`; definer privilege supplies table access. New functions must explicitly revoke default PUBLIC EXECUTE; service role alone does not establish owner identity for arbitrary account input.

Other events are recorded then ignored. New subscription linkage requires `subscription_created`; earlier noncreation deliveries defer. Refunds receive no new authority through neutral normalization.

Legacy creation currently permits a verified, checkout-linked subscription snapshot to create canonical paid state without the operation invoice predicate. This is **not** evidence that a generic `active` observation proves payment. Preserve v1 behavior for compatibility; v2 initial Paddle activation requires an explicitly verified completed transaction and linked subscription. Do not retroactively require unavailable invoices for historical LS records.
